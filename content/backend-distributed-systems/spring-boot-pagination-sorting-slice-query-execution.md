# Pagination, Sorting & Slice Query Execution

In [Lesson 15.1](/learning-paths/spring-boot-production-mastery) and [Lesson 15.2](/learning-paths/spring-boot-production-mastery), we built the core querying foundation of Spring Data JPA: the repository inheritance hierarchy, dynamic runtime proxy mechanics, method derivation, and custom JPQL/native queries.

However, in any production system that processes real-world traffic, you can never query an entire table at once.

A query like `accountRepository.findAll()` might work seamlessly in local development with 50 seed records. But in production, where tables grow to millions or hundreds of millions of rows, returning unconstrained result sets will exhaust JVM heap memory, trigger Stop-The-World garbage collection pauses, and saturate network bandwidth.

To serve large datasets safely, we must paginate.

Yet, pagination in Spring Data JPA is fraught with architectural traps that catch even experienced engineers:
- Why does returning a **`Page<T>`** trigger a hidden, secondary database query that can take **100x longer** than the actual data fetch?
- What is **`Slice<T>`**, and how does it enable infinite scrolling with **zero `count(*)` overhead**?
- What is the **"Offset Hell"** problem, and why does `OFFSET 1000000` degrade into a full table scan even when using an index?
- How do you implement **Keyset (Cursor-based) Pagination** to maintain constant $O(\log N)$ performance regardless of how deep a client paginates?

In this lesson, we will deconstruct pagination and sorting from first principles. We will inspect the SQL generated by `Pageable`, expose the hidden tax of `count(*)` queries, master `Slice<T>`, and implement production-hardened cursor pagination.

---

## 01. The Three Pagination Models in Spring Data JPA

When querying a subset of rows using a `Pageable` parameter, Spring Data JPA allows your repository method to return one of three return types:

```
+--------------------------------------------------------------------------------------------------+
|                            SPRING DATA PAGINATION RETURN TYPES                                   |
+--------------------------------------------------------------------------------------------------+
|                                                                                                  |
|   1. List<T> (Data-Only Offset Slicing)                                                          |
|   ─────────────────────────────────────                                                          |
|   List<Order> findByStatus(OrderStatus status, Pageable pageable);                               |
|   • Executes: 1 query with LIMIT and OFFSET.                                                     |
|   • Returns: The raw list of items on that page.                                                 |
|   • Does NOT know: Total elements, total pages, or whether a next page exists.                   |
|                                                                                                  |
|   2. Page<T> (Numbered Page Navigation)                                                          |
|   ─────────────────────────────────────                                                          |
|   Page<Order> findByStatus(OrderStatus status, Pageable pageable);                               |
|   • Executes: 2 queries (1 data query with LIMIT/OFFSET + 1 secondary COUNT(*) query).           |
|   • Returns: Items, total element count, total page count, hasNext(), hasPrevious().             |
|   • Best for: Traditional desktop UIs with numbered pagination buttons [ 1 ] [ 2 ] [ 3 ] ...     |
|   • DANGER: COUNT(*) query becomes an extreme bottleneck on large tables (> 1M rows).            |
|                                                                                                  |
|   3. Slice<T> (Infinite Scrolling / "Load More")                                                 |
|   ──────────────────────────────────────────────                                                 |
|   Slice<Order> findByStatus(OrderStatus status, Pageable pageable);                              |
|   • Executes: 1 query with LIMIT (requested_size + 1) and OFFSET.                                |
|   • Returns: Items, hasNext(), hasPrevious().                                                    |
|   • Does NOT execute COUNT(*). Completely eliminates the count performance penalty!              |
|   • Best for: Mobile apps, infinite scrolling feeds, and modern "Load More" interfaces.          |
|                                                                                                  |
+--------------------------------------------------------------------------------------------------+
```

## 02. The Hidden Tax of `Page<T>`: Why `COUNT(*)` Kills Throughput

### What Happens When You Return `Page<T>`?
Consider an e-commerce order management service that searches orders by customer ID:

```java
public interface OrderRepository extends JpaRepository<Order, UUID> {
    Page<Order> findByCustomerId(UUID customerId, Pageable pageable);
}
```

When your controller calls this method for page 0 with size 20:
```java
Page<Order> page = orderRepository.findByCustomerId(customerId, PageRequest.of(0, 20));
```

Hibernate intercepts the call and executes **two distinct SQL queries**:

```sql
-- Query 1: The Data Query (Retrieves 20 rows)
SELECT id, customer_id, total_amount, status, created_at 
FROM orders 
WHERE customer_id = 'e1a2b3c4...' 
ORDER BY created_at DESC 
LIMIT 20 OFFSET 0;

-- Query 2: The Mandatory Count Query (Calculates total elements)
SELECT COUNT(*) 
FROM orders 
WHERE customer_id = 'e1a2b3c4...';
```

### Why is the Count Query Catastrophic in Production?
In a small development database, `COUNT(*)` executes in less than 1 millisecond. 

However, in modern relational databases using Multi-Version Concurrency Control (MVCC) like **PostgreSQL**:
1. **There is no instantaneous row counter**: Because different transactions may see different snapshots of the data, the database cannot simply read an internal row count from table metadata.
2. **PostgreSQL must scan rows**: To count rows matching a condition (or even an unconstrained table), the database must perform an index scan or heap scan to verify transaction visibility (tuple MVCC headers).
3. **Joins Multiply the Cost**: If your query joins 3 tables (e.g., `Order` → `OrderItem` → `Product`), the count query executes the exact same complex join just to return an integer!

```
+--------------------------------------------------------------------------------------------------+
|                            THE ASYMMETRY OF DATA VS. COUNT QUERIES                               |
+--------------------------------------------------------------------------------------------------+
|                                                                                                  |
|   Table: orders (15,000,000 rows)                                                                |
|                                                                                                  |
|   Query 1: Data Query (LIMIT 20 OFFSET 0)                                                        |
|   ├── Index scan on `idx_orders_customer_created`                                                |
|   ├── Reads 20 index tuples and 20 heap pages                                                    |
|   └── Execution Time: 2.1 milliseconds  [LIGHTNING FAST]                                         |
|                                                                                                  |
|   Query 2: Count Query (COUNT(*))                                                                |
|   ├── Scans entire matching index subtree across millions of records                             |
|   ├── Evaluates visibility maps and table locks                                                  |
|   └── Execution Time: 4,850 milliseconds  [2,300x SLOWER!]                                       |
|                                                                                                  |
|   TOTAL ENDPOINT LATENCY: ~4.85 seconds (Dominated entirely by the count query!)                 |
|                                                                                                  |
+--------------------------------------------------------------------------------------------------+
```

Worse, this expensive `COUNT(*)` query runs on **every single pagination click**. When a user clicks Page 1, Page 2, Page 3, the database recalculates the exact same count repeatedly!

## 03. The High-Performance Alternative: `Slice<T>` for Infinite Scrolling

In modern web and mobile applications (e.g., social media feeds, chat histories, e-commerce product catalogs, notifications), users rarely care about knowing the *exact total number of pages*. 

Users only care about: **"Is there another page of data to show?"**

This is where **`Slice<T>`** shines.

### How `Slice<T>` Works: The `LIMIT + 1` Trick
When you declare your repository method to return `Slice<T>`:

```java
public interface OrderRepository extends JpaRepository<Order, UUID> {
    Slice<Order> findByCustomerId(UUID customerId, Pageable pageable);
}
```

If the client requests page size `20` (`PageRequest.of(0, 20)`):
1. Spring Data automatically modifies the SQL `LIMIT` clause to request **21 rows** (`size + 1`):
   ```sql
   SELECT id, customer_id, total_amount, status, created_at 
   FROM orders 
   WHERE customer_id = 'e1a2b3c4...' 
   ORDER BY created_at DESC 
   LIMIT 21 OFFSET 0;
   ```
2. **If the database returns 21 rows**:
   - Spring Data discards the 21st row.
   - It sets `slice.hasNext() = true`.
   - It returns the 20 requested rows to your application.
3. **If the database returns 20 or fewer rows**:
   - It sets `slice.hasNext() = false`.
   - It returns all fetched rows.

```
+--------------------------------------------------------------------------------------------------+
|                              THE SLICE<T> LIMIT + 1 ALGORITHM                                    |
+--------------------------------------------------------------------------------------------------+
|                                                                                                  |
|   Client requests: size = 5                                                                      |
|   Spring Data executes: SELECT ... LIMIT 6 OFFSET 0;                                             |
|                                                                                                  |
|   SCENARIO A: Database returns 6 rows                                                            |
|   ┌────┬────┬────┬────┬────┐ ┌────┐                                                             |
|   │ #1 │ #2 │ #3 │ #4 │ #5 │ │ #6 │ ◄── Spring Data drops row #6 and flags `hasNext = true`      |
|   └────┴────┴────┴────┴────┘ └────┘                                                             |
|   Returned to UI: [ #1, #2, #3, #4, #5 ] (hasNext = true)                                        |
|                                                                                                  |
|   SCENARIO B: Database returns 4 rows (End of data reached)                                      |
|   ┌────┬────┬────┬────┐                                                                          |
|   │ #1 │ #2 │ #3 │ #4 │ ◄── Count <= 5, so Spring Data flags `hasNext = false`                   |
|   └────┴────┴────┴────┘                                                                          |
|   Returned to UI: [ #1, #2, #3, #4 ] (hasNext = false)                                           |
|                                                                                                  |
|   TOTAL SQL QUERIES EXECUTED: 1 (Zero count queries. Zero waste.)                                |
|                                                                                                  |
+--------------------------------------------------------------------------------------------------+
```

### The Architectural Payoff
- **50% to 95% Latency Reduction**: Eliminates the secondary query entirely.
- **Constant Predictable Performance**: The database only ever reads `size + 1` records.
- **Native UI Alignment**: Directly maps to infinite scrolling, "Load More" buttons, and cursor-like mobile views.

## 04. The "Offset Hell" Problem & Keyset (Cursor) Pagination

While `Slice<T>` eliminates the `COUNT(*)` query, it still relies on **Offset Pagination** (`LIMIT n OFFSET m`).

In high-volume systems, Offset Pagination introduces two fatal flaws: **Deep Paging Degradation** and **Data Drift**.

### Flaw 1: Deep Paging Degradation
Suppose a client requests page 50,000:
```sql
SELECT * FROM orders ORDER BY id LIMIT 20 OFFSET 1000000;
```
How does the database engine process this?
1. The database cannot jump directly to row 1,000,000 in memory.
2. It must traverse the B-Tree index, load **1,000,020 rows** from disk, discard the first 1,000,000 rows, and return the final 20 rows!
3. As the offset `m` grows, query response time degrades linearly: $O(N)$. Deep paging will eventually time out or trigger database disk thrashing.

### Flaw 2: Data Drift (The Skipping / Duplicate Problem)
Imagine a user is viewing Page 1 (items 1–10). While they are reading:
1. Two new orders are placed and inserted at the top of the table.
2. The user clicks Page 2 (`OFFSET 10`).
3. Because two new rows shifted every existing row down by 2 positions, the items that were previously at positions 9 and 10 on Page 1 are now at positions 11 and 12 on Page 2!
4. **The user sees duplicate items** across consecutive pages. Conversely, if items were deleted, items would be silently skipped.

```
+--------------------------------------------------------------------------------------------------+
|                            OFFSET PAGINATION DATA DRIFT ANOMALY                                  |
+--------------------------------------------------------------------------------------------------+
|                                                                                                  |
|   INITIAL STATE:                                                                                 |
|   Page 1 (Offset 0, Limit 3): [ Order A, Order B, Order C ]                                      |
|   Page 2 (Offset 3, Limit 3): [ Order D, Order E, Order F ]                                      |
|                                                                                                  |
|   ACTION: 1 New Order (Order X) is inserted before user requests Page 2:                         |
|   Table state is now: [ Order X, Order A, Order B, Order C, Order D, Order E, Order F ]          |
|                                                                                                  |
|   USER REQUESTS PAGE 2 (Offset 3, Limit 3):                                                      |
|   Database skips first 3 rows: [ Order X, Order A, Order B ]                                     |
|   Database returns next 3 rows: [ Order C, Order D, Order E ]                                    |
|                                                                                                  |
|   BUG: The user sees `Order C` TWICE (on Page 1 AND on Page 2)!                                  |
|                                                                                                  |
+--------------------------------------------------------------------------------------------------+
```

## 05. The Solution: Keyset (Cursor-Based) Pagination

### What is Keyset Pagination?
Instead of telling the database how many rows to *skip* (`OFFSET`), **Keyset Pagination** uses the value of the last seen row's index key as a search anchor (the cursor):

```sql
-- Keyset Query: Jump directly to the next slice using B-Tree index seek
SELECT * FROM orders 
WHERE id < :lastSeenId 
ORDER BY id DESC 
LIMIT 20;
```

```
+--------------------------------------------------------------------------------------------------+
|                          KEYSET (CURSOR) PAGINATION ADVANTAGE                                    |
+--------------------------------------------------------------------------------------------------+
|                                                                                                  |
|   OFFSET PAGINATION: O(N)                                                                        |
|   OFFSET 1,000,000 ──► Must scan and discard 1,000,000 rows in memory!                          |
|                                                                                                  |
|   KEYSET PAGINATION: O(log N)                                                                    |
|   WHERE id < 'c1a2...' ──► Direct B-Tree Index Seek!                                             |
|   Database jumps straight to the exact index leaf page in microseconds.                          |
|   Performance on row 10,000,000 is identical to row 10!                                         |
|                                                                                                  |
+--------------------------------------------------------------------------------------------------+
```

### Implementing Keyset Pagination in Spring Data JPA
Let's see how clean and straightforward Keyset pagination is in practice:

```java
public interface OrderRepository extends JpaRepository<Order, UUID> {

    // First page query (no cursor available yet)
    @Query("""
        SELECT o FROM Order o 
        WHERE o.customer.id = :customerId 
        ORDER BY o.createdAt DESC, o.id DESC
        """)
    List<Order> findFirstPage(
        @Param("customerId") UUID customerId, 
        Pageable pageable
    );

    // Subsequent page queries anchored to the last seen timestamp & ID
    @Query("""
        SELECT o FROM Order o 
        WHERE o.customer.id = :customerId 
          AND (o.createdAt < :lastCreatedAt 
               OR (o.createdAt = :lastCreatedAt AND o.id < :lastId))
        ORDER BY o.createdAt DESC, o.id DESC
        """)
    List<Order> findNextPage(
        @Param("customerId") UUID customerId,
        @Param("lastCreatedAt") Instant lastCreatedAt,
        @Param("lastId") UUID lastId,
        Pageable pageable
    );
}
```

Notice the tie-breaker: `OR (o.createdAt = :lastCreatedAt AND o.id < :lastId)`. 
Because timestamps can have collisions, including the unique primary key `id` as a secondary sort key guarantees strict deterministic pagination without duplicates.

## 06. Sorting Mechanics & Security Traps

### Declaring Dynamic Sorting with `Sort`
Spring Data provides the `Sort` class to express multi-column ordering:

```java
// Single column sort
Sort sortByDate = Sort.by(Sort.Direction.DESC, "createdAt");

// Multi-column composite sort
Sort sortComposite = Sort.by("status").ascending()
                         .and(Sort.by("createdAt").descending());

// Passing Sort to repository
Pageable pageable = PageRequest.of(0, 20, sortComposite);
```

### The Unindexed Sort Disk Spill Trap
When a client requests sorting via query parameters (e.g., `?sort=customerNotes,asc`), if `customerNotes` is not indexed:
1. The database cannot use an index to satisfy the ordering.
2. It must pull all matching rows into working memory (`work_mem` in PostgreSQL).
3. If the dataset exceeds `work_mem`, PostgreSQL spills the sort to **temporary disk files** (`external merge sort`), tanking database I/O.

> [!CAUTION]
> **Never allow clients to sort by arbitrary columns.** 
> In your service layer or controller, maintain an allowlist of permissible sort properties that have supporting B-Tree indexes. Reject or sanitize any unauthorized sort fields.

```java
// Production Sort Sanitization
private static final Set<String> ALLOWED_SORT_FIELDS = Set.of("createdAt", "totalAmount", "id");

public Pageable sanitizePageable(Pageable pageable) {
    Sort safeSort = Sort.unsorted();
    for (Sort.Order order : pageable.getSort()) {
        if (ALLOWED_SORT_FIELDS.contains(order.getProperty())) {
            safeSort = safeSort.and(Sort.by(order.getDirection(), order.getProperty()));
        }
    }
    return PageRequest.of(pageable.getPageNumber(), pageable.getPageSize(), safeSort);
}
```

## 07. Complete Production Code Reference: High-Scale Order Feed

Let's assemble these pagination models into a clean, production-grade Spring Boot service demonstrating:
1. An admin endpoint using `Page<T>` with an optimized count query.
2. A customer mobile feed using `Slice<T>` with zero count overhead.
3. A high-throughput audit stream using Keyset Cursor pagination.

### Step 1: The Domain Entity
```java
package com.example.domain.order;

import jakarta.persistence.*;
import java.math.BigDecimal;
import java.time.Instant;
import java.util.UUID;

@Entity
@Table(
    name = "orders",
    indexes = {
        @Index(name = "idx_orders_customer_created", columnList = "customer_id, created_at DESC, id DESC"),
        @Index(name = "idx_orders_status", columnList = "status")
    }
)
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.UUID)
    private UUID id;

    @Column(nullable = false)
    private UUID customerId;

    @Column(nullable = false, precision = 12, scale = 2)
    private BigDecimal totalAmount;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 30)
    private OrderStatus status = OrderStatus.PENDING;

    @Column(nullable = false, updatable = false)
    private Instant createdAt = Instant.now();

    protected Order() {}

    public Order(UUID customerId, BigDecimal totalAmount) {
        this.customerId = customerId;
        this.totalAmount = totalAmount;
    }

    public UUID getId() { return id; }
    public UUID getCustomerId() { return customerId; }
    public BigDecimal getTotalAmount() { return totalAmount; }
    public OrderStatus getStatus() { return status; }
    public Instant getCreatedAt() { return createdAt; }
}

public enum OrderStatus {
    PENDING, PROCESSING, COMPLETED, CANCELLED
}
```

### Step 2: The Production Repository
```java
package com.example.domain.order;

import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;
import org.springframework.data.domain.Slice;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;

import java.time.Instant;
import java.util.List;
import java.util.UUID;

public interface OrderRepository extends JpaRepository<Order, UUID> {

    // 1. PAGE<T> WITH OPTIMIZED COUNT QUERY (For Admin UIs requiring exact total count)
    @Query(
        value = "SELECT o FROM Order o WHERE o.status = :status",
        countQuery = "SELECT count(o.id) FROM Order o WHERE o.status = :status"
    )
    Page<Order> findAllByStatusForAdmin(
        @Param("status") OrderStatus status, 
        Pageable pageable
    );

    // 2. SLICE<T> (For Mobile & Web Infinite Scroll - ZERO COUNT QUERY)
    Slice<Order> findByCustomerIdOrderByCreatedAtDesc(
        UUID customerId, 
        Pageable pageable
    );

    // 3. KEYSET CURSOR QUERY (For High-Volume, Deep Infinite Scrolling)
    @Query("""
        SELECT o FROM Order o 
        WHERE o.customerId = :customerId 
          AND (o.createdAt < :lastCreatedAt 
               OR (o.createdAt = :lastCreatedAt AND o.id < :lastId))
        ORDER BY o.createdAt DESC, o.id DESC
        """)
    List<Order> findNextKeysetPage(
        @Param("customerId") UUID customerId,
        @Param("lastCreatedAt") Instant lastCreatedAt,
        @Param("lastId") UUID lastId,
        Pageable pageable
    );
}
```

### Step 3: The Application Service Layer
```java
package com.example.service;

import com.example.domain.order.*;
import org.springframework.data.domain.Page;
import org.springframework.data.domain.PageRequest;
import org.springframework.data.domain.Pageable;
import org.springframework.data.domain.Slice;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.time.Instant;
import java.util.List;
import java.util.UUID;

@Service
@Transactional(readOnly = true)
public class OrderQueryService {

    private final OrderRepository orderRepository;

    public OrderQueryService(OrderRepository orderRepository) {
        this.orderRepository = orderRepository;
    }

    /**
     * Admin Portal: Numbered page navigation (executes data + count query).
     */
    public Page<Order> getOrdersForAdmin(OrderStatus status, int page, int size) {
        return orderRepository.findAllByStatusForAdmin(status, PageRequest.of(page, size));
    }

    /**
     * Customer App: Infinite scroll feed (executes single query with LIMIT size + 1).
     */
    public Slice<Order> getCustomerOrdersFeed(UUID customerId, int page, int size) {
        return orderRepository.findByCustomerIdOrderByCreatedAtDesc(customerId, PageRequest.of(page, size));
    }

    /**
     * High-Scale Feed: Keyset cursor pagination (O(log N) constant B-tree seek).
     */
    public List<Order> getCustomerOrdersByCursor(
            UUID customerId, 
            Instant cursorCreatedAt, 
            UUID cursorId, 
            int limit) {
        
        Pageable pageable = PageRequest.of(0, limit);
        
        if (cursorCreatedAt == null || cursorId == null) {
            // Initial page
            return orderRepository.findByCustomerIdOrderByCreatedAtDesc(customerId, pageable).getContent();
        }
        
        // Next cursor page
        return orderRepository.findNextKeysetPage(customerId, cursorCreatedAt, cursorId, pageable);
    }
}
```

## 08. Production Case Study: The 15-Million-Row Admin Dashboard Lockup

### The Incident
A fast-growing e-commerce marketplace maintained an internal Operations Portal used by 200 customer support representatives. 

The dashboard displayed a table of orders filtered by status:
```java
@GetMapping("/admin/orders")
public Page<OrderDto> getOrders(
        @RequestParam OrderStatus status, 
        @RequestParam(defaultValue = "0") int page, 
        @RequestParam(defaultValue = "20") int size) {
    return orderService.getOrders(status, PageRequest.of(page, size));
}
```

When the platform had 100,000 orders, page requests responded in 35 milliseconds. 

Two years later, after the platform grew to **18,000,000 orders**:
1. Support agents clicking through order pages experienced response times of **8 to 14 seconds** per click.
2. During peak morning hours, multiple agents simultaneously opened the dashboard, triggering 30 concurrent `COUNT(*)` queries on the `orders` table.
3. PostgreSQL CPU spiked to 100%, query buffers filled, and standard checkout transactions began timing out.

### The Root Cause Analysis (RCA)
Database query telemetry isolated the bottleneck:
- The data query:
  ```sql
  SELECT * FROM orders WHERE status = 'PENDING' ORDER BY created_at DESC LIMIT 20 OFFSET 40;
  ```
  Executed in **3.2 milliseconds** via the composite index `(status, created_at)`.
- But Spring Data automatically issued:
  ```sql
  SELECT count(*) FROM orders WHERE status = 'PENDING';
  ```
  Because PostgreSQL had to verify tuple visibility across 2.4 million pending orders, the count query scanned over **45,000 database pages**, consuming **11.8 seconds of CPU time**.

The total endpoint duration was 11.83 seconds—and 99.97% of that time was spent computing a total page count that agents rarely even looked at!

### The Remediation
The engineering team executed a two-pronged solution:
1. **Replaced `Page<Order>` with `Slice<Order>` on customer-facing and operational feeds**:
   Support workflows were updated to use a modern "Next / Previous" pagination UI powered by `Slice<Order>`.
2. **Decoupled and Estimated Total Counts**:
   For the few administrative reporting views that strictly required total counts, the team decoupled the count query:
   - Evaluated PostgreSQL table statistics (`pg_class.reltuples`) for instantaneous $O(1)$ estimates.
   - Or cached the accurate count in Redis with a 15-minute TTL, eliminating the per-request database count penalty.

### The Result
- Average dashboard endpoint latency dropped from **11.8 seconds** to **4 milliseconds**.
- PostgreSQL database CPU utilization plummeted from **100%** to **14%**.
- Connection pool wait times dropped to 0.

## 09. Architectural Mental Map & Summary

To ensure you choose the correct pagination model for every use case, use this operational mental map:

```
+==================================================================================================+
|                        SPRING DATA PAGINATION ARCHITECTURAL MENTAL MAP                           |
+==================================================================================================+
|                                                                                                  |
|   1. PAGINATION STRATEGY DECISION TREE                                                           |
|      ──────────────────────────────────────────────────────────────────────────                  |
|      Does the UI strictly require numbered page buttons (e.g. [1] [2] [3]...)?                   |
|        │                                                                                         |
|        ├── YES ──► Use `Page<T>`                                                                 |
|        │           • Be aware of secondary `COUNT(*)` overhead.                                  |
|        │           • Provide explicit, lean `countQuery` in `@Query`.                            |
|        │           • Cache total count in Redis if table has > 1,000,000 rows.                   |
|        │                                                                                         |
|        └── NO  ──► Is it an infinite scroll feed, mobile view, or "Load More" UI?                |
|                      │                                                                           |
|                      ├── Typical scale (< 100k rows, shallow navigation):                        |
|                      │   ──► Use `Slice<T>`                                                      |
|                      │       • Zero count queries (LIMIT size + 1).                              |
|                      │       • O(1) count overhead; fast and native.                             |
|                      │                                                                           |
|                      └── High scale (> 1M rows, deep navigation, real-time updates):              |
|                          ──► Use KEYSET (CURSOR) PAGINATION                                      |
|                              • WHERE (created_at, id) < (:cursorTime, :cursorId)                 |
|                              • Constant O(log N) index seek.                                     |
|                              • Completely immune to data drift and deep page slowdowns.          |
|                                                                                                  |
|   2. COMPARISON MATRIX                                                                           |
|      ┌──────────────────┬──────────────┬──────────────┬──────────────┬───────────────────────┐   |
|      │ FEATURE          │ List<T>      │ Slice<T>     │ Page<T>      │ Keyset Cursor         │   |
|      ├──────────────────┼──────────────┼──────────────┼──────────────┼───────────────────────┤   |
|      │ Total Queries    │ 1            │ 1 (size + 1) │ 2 (Data+Cnt) │ 1                     │   |
|      │ Count Overhead   │ None         │ None         │ ExtremelyHigh│ None                  │   |
|      │ Know Total Pages │ No           │ No           │ Yes          │ No                    │   |
|      │ Know HasNext     │ No           │ Yes          │ Yes          │ Yes (with size + 1)   │   |
```
